# 出图循环与闸的执行口径（mechanical-homework 支撑文件）

**什么时候读**：出零件图、改图、跑闸、被退图的时候。本文件是 `SKILL.md` 原「开工前」节搬出来的执行细则——主文件只留动手前的硬约束，这里放「怎么画、怎么验、闸怎么用」。
规则原文照搬，口径未改；条数与命令参数以本文件与 `charter/README.md` 现读为准，别抄写死的数字。

目录：

1. 参考件怎么读
2. 干活节奏（轮次、自测、停手线）
3. 自检与验收的边界
4. 闸：期望值、调用、四态与盲区
5. 查库接口用反射

## 一、参考件怎么读

- **「既有版本」指用户自己成品图里那一版，不是自己现编的**：`10-6解答/大齿轮零件图.svg` 的 **152×40 四行全封闭栏**（名称格跨两行 / 材料·45·图号值 / 比例·1:2·图号标签 / 制图行 / 审核行），结构见 `references/gb-gear-drawing.md`「标题栏」。动手前先拆那张图的代码核行数与格宽：如果自己这边现在是三行/无比例栏，那是错的，照用户的图重画——但**图号、人名、单位这类内容仍按本题填完再问用户**。
**参考件/样例先读身份再用，别按文件名认**：同名文件可能是别人那张图。拿之前读根节点的 `width/height`、`<title>`、标题栏 rect 的宽高与图号——「输出轴零件图.svg」完全可能是 1:1、180×56 标准式栏的外部参照件，而不是自己那份 1:2、152×40 的成品；拿错源会把「统一标题栏」做成把对的改成错的。对不上就先说清它是什么、再问换不换源。
**范式图的价值在「信息分层」，不在一根线标一个数**：拿到参考件先找它把哪些要求**搬出了图面**——同一公称直径多区段要求 → 分区表；重复的工艺要求 → 技术要求条目；通用粗糙度 → 统一注法 (√)。自己的出图脚本若还是「一个参数一个标注」的数据结构，改坐标是补不出这张图的，先改 schema（区段表 → 标注入口）再画。

## 二、干活节奏（轮次、自测、停手线）

- **文档里的待办是排序，不是菜单**：`ITERATIONS.md` §8 那类待办表是按「能挡住的错误」排过序的，**从第 1 项往下做**，不许挑便宜的、好改的先做——挑两项小的交差，前面两项大的照样没动，等于没按计划推进，会被当场质问「你当顺序是摆设吗」。做完一项就在表里标完成 + 写实测证据（数字、命令输出），再动下一项。
- **「更新文档」指干活那个仓库自己的迭代文档**：改了 mdkit 的闸就更新 `lib/drawing/charter/ITERATIONS.md` + `charter/README.md`（§0 规则数、§5 实测数字、§6 提交哈希、§8 待办状态一起改），不是同目录的旁支汇总文件（自建的目录账本之类）。用户问「做完不更新文档？」时指的几乎总是前者；猜错就是白干一轮。
- **一次改完，一次验；轮次就是唯一的成本**：改图循环里先把所有要改的一起改（坐标、标注、结构、参数），再跑一次 `devloop.sh`（`mdkit/lib/drawing/charter/devloop.sh`；**它是 shell 脚本，用 `bash` 起，写成 `python3 …devloop.sh` 必 `SyntaxError`**）（build + check + 整页截图 + 按 `data-view` 裁局部，一次调用把所有图片路径给全）；**`devloop.sh` 支持 `--part` / `--features` 透传，要自己传**：不传就只跑 L0~L3 + common，零件层 P-01~P-05 / P-11~P-13 不执行；退出码 0 无 ✗ / 1 有 ✗ / 2 build、截图或检查器失败（有 ✗ 时截图照出，方便看错在哪）。**交付前的最后一跑仍要直调 `check.py` 全参**，别把 loop 的 0 当通过信号——0 只代表「没有 ✗」，可能带一堆「未检查」；**跨项目工具一律放这个目录，别塞进某个项目里**——写进项目目录、PROMPT 与 skill 又没同步，下一个项目根本不会去翻它，等于没写（实测：工具建好后 11 小时内的新项目一次都没调用过，自己又重写了一套等价的）；不要「改一处 → build → check → 截图 → vision」小步走。实测一张新图从零这样画：40 次 build、44 次 check、35 次 `mutants.py`、47 次 vision、21 次局部裁剪，总时长 46 分钟，而**工具总耗时只有 2.4 分钟（5%）**，其余全是 222 次工具调用之间的模型决策（≈12 秒/次）——慢的不是检查器（单次全量 0.7 s），是轮次。三条硬规则：循环里**不跑 `mutants.py`**（图没变、检查器没变，跑它零信息，一次就是 17 个注入）；循环里**不逐轮 vision**——截图并进 `devloop.sh` 那一次调用，一轮只看它裁出来的 2~4 张（压线/重叠/箭头/界线检查器都查了，vision 只判整体观感与版式，数字与线位一律不用它）；同一轮的多处修改**合成一次 `execute_code` / `patch`**，别一处一个调用。目标 ≤10 轮，超过 15 轮就是在 micro-fix，按「同一张图被退两次」停手重排。
- **生成器先自测再画图**：新写的 `build_*.py` 先给几何函数配几条坐标断言（`assert abs(x - 期望) < 0.01`、台阶/圆心/端点各一条）再连着出图。实测一轮绘图里 6 次 Traceback（KeyError×3、TypeError×1、assert 失败×6）全部出在「改完直接 build」，每次都要重读代码再改，比写断言贵得多。
- **改图前先过清单，不是事后查百科**：`references/part-drawing-a3.md`、`gb-gear-drawing.md` 里的条目是**出图前逐条打勾的检查表**。同一类错（漏封闭线、倒角反向、剖面比例、尺寸界线、字体与标题栏）被指出第二次，先怀疑“没照着清单过”，而不是“缺一条规则”——再补一条新规则，下一次还是照旧漏。
- **同一张图被退两次就停手重来，别接着 micro-fix**：连续几轮只改坐标、改引线位置而结论仍被否，说明错在**结构与画法判断**上（整套台阶轮廓、投影关系、剖切范围），不是在毫米上。停下渲参考件/手册图成 PNG 与自己的图**并排逐项对**，改版式与结构，别再在坐标上打补丁。**并排时逐条数线**（母线／竖线／斜线／端面各几条），只比「看着像不像」会整条线漏过去；参照的必须是**用户给的那张参考件**，不是套件样例、也不是自己上一版——它们和你同源，一起错。

## 三、自检与验收的边界

- **自检不等于验收，措辞要分开**：交付只陈述“改了什么、依据哪张参考图/手册图、哪几处没做/没核”。像素采样、断言全绿、测试退出码这些是**自检结论**，不是图正确的证据；把它们写成“已核/已验证”，用户会当成你替用户签了字——这是图纸被反复退回的直接原因之一。**闸绿的边界也要说清**：L3 只判「文字×线」，「尺寸线/界线穿过轮廓」（例如压在键槽长圆、剖面线上）压根没有判据——实测一张 51/51 全绿的轴图仍有尺寸线穿槽。交付前整页目视一次，并把这类无判据项写进“未覆盖”清单。**回话里点名跑的是哪条闸**：`check.py` 全参（`--calc/--features/--fig-no/--part`）、`devloop.sh`、`--selftest` 三者覆盖面不同，只写「51/51 通过」会被反问「mdkit 的绘图校验流程跑了吗」；同时写清倒角长度、尺寸线穿轮廓这类无判据项是自己目视/像素核的，不能混进「已核」。

## 四、闸：期望值、调用、四态与盲区

- **闸与生成器不许共用期望值**：`核查*.py` 里出现尺寸/字段字面量、或 `import model` 拿同一份数据当“标准”，就只能证明「我按自己的错继续错」——上一版的错结构一旦被抄进白名单，错图永久通过。期望值必须来自独立来源（计算书 json / 参考件 SVG 源码 / 标准表）；每个图元带 `data-role` + `data-feature`，缺元数据算「不通过」不是「跳过」；`未检查` 与规则异常一律 exit 1；闸自己要被变异测试（注入的错误全部抓住才算可用）。设计口径与变异用例见 `references/drawing-gate.md`。
  - **闸已落地，别再另起一套**：`mdkit/lib/drawing/CHARTER.md`（145 条，A/M/X 三态）+ `charter/rules.json` + `build_charter.py` / `check_charter.py` / `gen_api.py` / `check_contract.py` / `identify.py`，语义层 `lib/drawing/sem.py`。交付前**一条命令**跑完：`python3 lib/drawing/charter/check.py 图.svg --calc <calc.json> --fig-no <图号> --part shaft|gear`（L0~L3 + common/part；`--selftest` 连 L4，`--no-browser` 跳量测，`--json` `features.json`，两张图共用一个名字等于互相覆盖，而且拿错清单的检查不会报错——只会按别人的轮廓判「缺失」或默认全过。共用目录里先 `ls -la` 看 mtime 再写：别的会话可能正在写同名产物，别顺手 `rm` 掉别人的 `features.json` / `print.html`。入口把 measure → L0 → L1-L3 的顺序固定死，末尾把「未检查」单列——**手动拆开跑时 `--bounds` 漏传，L3 六条全变「未检查」而汇总行仍写「N 通过」，像没事一样**，这是这套闸最容易被误读的一处。单层调试才手动走：`identify.py 图.svg --write`（缺身份时，改完做像素回归）→ `measure.py 图.svg -o bounds.json` → `check_contract.py `features.json`）；**`mutants.py` 的四种结果要分开看**：抓到 / 漏抓（规则没红）/ **跳过(环境)**（规则因本机缺依赖判不了——缺 fontTools 时 G-13 只能出「未检查」，记跳过并在汇总里点名，不算漏抓、也不算通过）/ 注入未生效（改完图跟原图一样，用例本身坏了）；缺 Chromium 更前置：直接提示 `CHROME=<可执行文件>` 并 exit 2，别把「没装浏览器」当成检查器盲区去补规则——第三种最像漏抓，靠注入前后比哈希挡住，正则没匹配、属性顺序记错都会让 `edit` 静默返回原文；**盲区已清零**：键槽开口方向由 `L1-11` 覆盖（断面槽底在圆心哪一侧＝剖切箭头指向哪一侧，同图自洽约定，不是国标原文），`mutants.py` 24 注入 24 抓到、0 登记盲区；别再把它列成人工项，也别把 `known_gap`   - **条款映射与夹具是这个闸的地基，动之前先看这三条**：①规则的第三个参数是条款号，必须存在于 `rules.json` 且状态为 `A`；`check_charter.py` 会 import 规则注册表校验映射（不存在 / 状态非 A / 规则号重复 → exit 1）——改了规则挂哪条条款，就要同步把该条款标 A 再重生成 CHARTER.md，否则一致性脚本红；②L4 的底图与计算书在 `charter/fixtures/`（样例-输出轴、中间轴、齿轮零件图 + 各自 calc/features），**不要把 `mutants.py` 的常量指到 `~/Documents` 下的项目目录**——那边一清目录，注错反测不是报错而是静默跑完；夹具缺失时脚本 exit 2 并列缺哪个；③`check.py` 的退出码契约：0 无 ✗ / 1 有 ✗ / **2 检查器或输入异常**（坏 `--calc`/`--features` 也是 2，报「这是输入错，不是图错」）；汇总行按「L0 n + L1~L3 n + common/part n（合计 n）」分列印，读汇总时别再拿「L1~L3 29 条」当总数。规则条数、A 覆盖数、注入数一律现读 `check_charter.py` / `mutants.py` 的输出，不抄这里的数字。**写或改任何一层规则前先读 `references/drawing-gate.md` 的「3½ 配对判据」「3⅝ 几何层」「3¾ 身份补齐」「3⅞ 碰撞层」「3Ⅹ 变换层」「3Ⅺ 字形覆盖」「3Ⅻ 视图归属」**：name 覆盖率不满格时按 name 分组会静默落空，读数要取尺寸线上的箭头尖间距而不是线长；缺角色时新增角色，别硬塞进近似的。
  - **闸只查「画出来的东西对不对」，查不了「该画的没画」**：L0~L3 全部以「图上已有图元」为前提，漏画的线四层一起沉默——实测两次都是闸 0 不通过、用户看预览图才发现（齿轮漏远侧可见轮廓 + 孔口竖线共 8 条；轴漏轴肩阶梯线中段）。补法是 **L2-10 + 生成器导出的 `features.json`**：清单声明「应该有哪些轮廓」，检查器按共线段的**并集覆盖**比对（≥95%，合并允许 0.3mm 接缝——圆角切点处本来就会拆段），不足时报最大缺口的位置与长度，不是只说一句「缺了」。三条硬口径：①清单必须由生成器的**几何模型**算出（`X[]/R[]` 现算），**不许从 SVG 反推**——反推永远自洽，只证明「抄得对」；②坐标与 SVG 属性同一套（y 向下），生成器内部若 y 向上，导出时 `fy = H - y` 翻转，两边坐标系混了会 16/16 条全报缺失；③没有清单判**未检查**，不判通过。它挡的是「想到了但画漏了」，挡不了「压根不知道要画」——后者要靠画法规则。
  - **判据不完整时，agent 会为了变绿去改画法**：L2-01 只判「端点有没有接上（≤0.5mm 缝隙）」，为了让轴肩线通过，把一条该画满大直径的线砍成两截短头，中段 63mm 丢了——闸绿了、图错了。**规则只罚「缝隙」就会奖励「缩短几何」**。所以修一条「缝隙」类报红之前，先确认这条线本来该画多长（画法依据在哪条 GB/参考件）；能写成**覆盖类**判据（「该盖的都盖了」）就别用「别留缝」。
  - **闸红先分「图错」还是「契约缺口」**：图上标了计算书没登记的尺寸就报红，最典型是齿轮图 P-13——线性集只收 `输入.几何.b` / `结构.hub_l` / `结构.web_t`，而键槽宽 `14 JS9` 出自键表（`键.*.b`），一标就红。这类是**契约缺口，图是对的**：别改图去迁就，也别擅自改 `part/*.py`（那是用户自己的工具仓）——交付里点名这条、给出修法（把 `键.*.b` 补进线性集，一行），并说明它不影响图面正确性；「未检查」同理，逐条列出而不是算进绿。
  - **同一类错在不同项目出现第二次，沉进 charter，不是每个项目重写第二层检查器**：两轮同类绘图练习各写了 800 行 `selfcheck.py`，字体（仿宋嵌入/无回退）、线宽分层、尺寸齐全性、图形侵入表格、腔体闭合、无 A 弧这六条措辞几乎一样，纯重复劳动且质量不一（齿轮 17 条配 19 条注错反测，轴 22 条只配 5 条——后者大半绿灯没有判别力证明）。通用能力沉到 `charter/common/*`（字体、线宽、GB/T 1182 基准符号与跳动符号、表格压线）；零件类型相关的沉到 `charter/part/*`（齿部三线、轴肩画满、键槽长圆、基准三角方向），**别再把这些直径/零件名写死进项目脚本**——`基准 A/B 三角底边贴 φ55` 这种换根轴就废。

## 五、查库接口用反射

- **查库里的接口用反射，不用 grep 名字**：`_prim.py` 把 gbdraw 原语按中文名重导出（`线 = gbdraw.L`、`圆 = gbdraw.CIRCLE`、`弧 = gbdraw.ARC`…），`grep -n "^def \|^[A-Z_]* ="` 抓不到赋值形式的别名——照这个结果断言「库里没有这个函数」会直接判错、还会把对的接口表说成假的。用 `hasattr` / `inspect.signature`，或看 `charter/api.md`。

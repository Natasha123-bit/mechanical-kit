## 批次验收（外部 agent 跑批：验收 → 发「继续」→ 下一批）

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

用户把一本**图样标准**（`drawing` 这种）交给 ZCode 一批一批跑、Hermes 当验收方时，五条硬规矩：

1. **交批靠文件契约，不靠聊天文本**：任务书写 `PAUSED-批N.md` + 进度表「待验收」，监视器只判这两样；进度表要按**表格行**匹配 `\|\s*待验收`（正文里也常出现这个词）。**单章收口也会写「待验收」，那不是交批**——一批含多章时判据必须是「`PAUSED-批N.md` 出现」或「本批各章全部到待验收」，只判一行会让监视器在第一章就报交批；监视器退出时把已交章号打出来，方便一眼看出是整批还是单章。监视器本身（活动量判定、`finishReason` 语义、怎么把「继续」送进去）见 skill `zcode-desktop` 的「眛跑批」节，不在这里重写。
2. **不采信自述的数字，重算一遍**：它说「17 个画法函数 / 1063 个图元」，就用 `inspect` 枚举模块里的全部可调用函数、逐个 `len(图形)` 求和；它说「6 张图 59 处命中」，就自己重跑 `draw/chNN/build.sh`（实测 3 分钟）看 `RESULT: PASS`。数字对不上是最省力的信号，对得上也不代表内容对——还要抽表。
3. **线宽与线型用 AST + 像素裁定，`vision` 不算证据**：`vision` 会把 0.22 mm 的细线看成粗线，并据此判「粗粗重合，明显错画」（实测误报）。做法：把 AST 里某条 y 上的所有水平线按 `style` 导出（未旋合/旋合、左/右半各取一处），再用 `check/verify_drawing_lines.py --scan x=…` 竖向扫线段量宽度。`vision` 只回答「像不像一张图」（有无重叠、出界、缺视图、剖面线漏画）。
4. **契约文件被改要单查**：`ls -la lib/<book>/*.py` 看字节数与 mtime。`_prim.py` 这类接缝文件被改时，逐个确认是**加法**（新增 `平移()` 这类原语）而不是放宽校验（`校验图元` 仍 `strict=True`、线型白名单没扩）。任务书里补一句「改契约文件必须在回执单列一行」，否则它只会写在聊天里。
   反过来，**你自己发现 `_lookup.py` / `_anno.py` 有缺陷时也不要在跑批期间改**：对面正在 import 这个文件，换解析器会与它当下那批测试结果交叉。把缺陷连证据写进 `_批队列.md` 的修复清单（哪张表哪一行、哪个输入值查不到、实测报错原文），**批末统一修**：补形态 → 跑全部 `*_tests.py`（断言只增，必须仍全绿）→ 复跑 `scripts/check_lookup_ranges.py`。用户会直接选这条（“不在跑批期间动它正在用的文件”）；默认就按它做，不用再问。
   **验收通过之后再升级共享件，不回改验收记录。** 那些文档证明的是当时的 sha，改了等于让证据跟着结论走。做法是新建 `books/<book>/契约变更.md`，逐条记「文件 / 旧 sha 前 16 位 / 新 sha / 变更性质（纯追加？既有函数动没动）/ 验证（多少项断言、页图核了哪几格）」，验收文档一字不动；下次有人问「契约 sha 对不上」，先看这份再谈是不是被偷改。
5. **派活走 ZCode 自带 CLI，不靠窗口注入**：`node ~/.hermes/cache/scratch/zcli/zcode.cjs -p "$(cat dispatch.md)" --cwd books/<book> --mode yolo`，后台跑 + 监视器。桌面窗口只能注入「用户正开着且空闲」的那一个会话，它停在别的任务上时贴过去会搅掉别人的上下文，锁屏时更是全部无效。代价是**跑批期间侧栏看不到它**（跑完冷启动桌面版才把它同步进「任务」列表，⌘R 不刷新）——派活时就要说明日志与 rollout 路径、结果由你逐批汇报。镜像与 provider 坑见 skill `zcode-desktop` 的「不碰 UI 派活」节与 skill `zcode-desktop` 的 `scripts/zcode_headless.sh`。
   **查活要用 `ps aux | grep zcode-cli`，别用 `pgrep zcode.cjs`。** node 启动后把进程标题改成 `zcode-cli`，按命令行匹配 `zcode.cjs` 是**假阴性**——据此判死会起一个 `--resume` 重复会话，两个 agent 同时改同一条会话（2026-10-22 实测踩到，2 分钟内杀掉才没坏事）。派活后第一件事是 `ps aux | grep zcode-cli` 记下 pid。
   跑批进程要**真脱离**（关 Hermes/`/new`/压缩都不能带走它）：macOS 没有 `setsid` 命令，用 `python3 ~/.hermes/skills/engineering/mechanical-book-deposit/scripts/daemonize.py /bin/sh -c 'exec node zcode.cjs …'`（fork+setsid+execvp，打印子进程 pid 后立即返回）。脱离后 PPID=1，**Hermes 界面的「后台任务」永远列不出它**，用户会问「怎么看不到在跑」——回答要拿 `ps` 证据，别说「在界面上能看到」。监视器则相反：用 `terminal(background=True, persist_on_release=True)` 直接跑，`exec python3 watch.py` 让被跟踪的 pid 就是它本身；写成 `nohup … & echo pid` 会让启动 shell 立刻退出，任务在界面里标成 completed 而孤儿进程还在跑——界面上看不到、也管不住。
   **派活前先锁 provider，这是本类任务最贵的一个坑**：CLI 没有 `--model` 参数，默认吃 `~/.zcode/v2/provider_config.json` 的 `providerOrder[0]`；同一个模型名（`deepseek-flash`）可能同时挂在厂商官方与聚合网关，名字对得上不等于家对。顺序不对就会拿最贵那条跑一整批。开跑 60 秒内查 `model_usage.provider_id`，不对立刻 kill；用户点名主选+备选时，把这条链写进派活结论（主选挂了换备选 → 备选也挂就停，不降第三个），步骤见 `zcode-desktop/references/model-provider-pinning.md`。**用户点名要订阅 plan（`account:`）的模型时，先按那份文档第 4 小节查 `entitled`**：为 `false` 时 headless 根本选不上它，会静默退回 `providerOrder` 下一个 provider + `max` 档——这时别用真派活去试，先把结构告诉用户（桌面端起任务 / 修登录 / 换回 API-key 家）。
   **档位同样要钉**：任务书里的模型白名单管不到思考强度，CLI 不给档位时落模型自带最高档（`max`），实测过度思考、成本失控；这类沉淀跑批用户要求统一 `high`。用 `provider_config.json` 的 `defaultModelSelection.options.reasoningLevel` 钉死，验收看 `model_usage.variant`。且**会话的 provider/model 在创建时就钉死，`--resume` 换不了**——改完配置必须新开会话重跑该批，旧会话只能接着用原模型。
   查 `~/.zcode/cli/db/db.sqlite` 用**普通连接**：加 `?mode=ro&immutable=1` 会跳过 `-wal`，刚写进去的 `model_usage` 行 / `local_setting` 修改读不到，会误判「配置没生效」「没开出新会话」。确认办法：不带 `immutable` 再查一次，两次数值不同就是被 WAL 坑了（只读查询本身安全，ZCode 正在跑也能查）。
   开工第一回合必须让它回四行：**能否调子代理（并发几个）、实际 provider+model、材料自检结果、读图自检结果**——不给这四行就是回到单代理串行读图，正是用户要避免的；模型不在任务书白名单里当场重派。读图自检的做法：让它裁一张目标页的图例/刻度区并用一句话说出画面内容（能说出来才算视觉通了），任务书里同时写明「视觉负责认图例、分线型、找交叉，落库的每个数必须有像素证据，视觉可否定不可单独确立」。判定模型支不支持图片要查 provider 配置里 **builtin 的 `modelMatch` 规则**的 `inputFormat.supportsImage`，**不能因为 provider 级 override 里缺 `inputFormat` 字段就断言「无视觉」**——override 只写它要覆盖的字段（contextWindow / 网络 / 中插系统消息），缺字段不等于不支持。

## 执行方并发上限小于默认分工时怎么排

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

默认角色表是 6 个/章（表值前后半、判据、标注、勘误、建库）。用户把并发压到「主代理 + 2 个子代理」这类上限时，**不要硬塞角色，改波次**——任务书的角色表整节重写，别指望执行方自己降级：

| 波次 | 子代理① | 子代理② | 主代理 |
|---|---|---|---|
| 1 | B 表值核读：**每 8–12 表分一段，每段新开一个子代理、段间串行**（见下条） | E 勘误/边界 + 先出「表号 → 页 → 页图」定位表 | 落盘骨架、查材料缺口 |
| 2 | C 判据（读齐 B 才开工） | D 标注复现（等 C） | F 建库 + 双解释器（自己做，不占位） |

- 硬闸不变：B 没回来 C 不开工、章内自检没绿不开下一章、批末照旧停。章内墙钟比 6 并发长约 1.5–2 倍，把这个倍数写进工期预估，别按原口径报时间。
- **定位表（`00-清单.json`）必须主代理先算好**：2 并发下若两个子代理各自翻页找表，省下来的并发全花在重复查找上。
- 每章设时间盒（如 3.5 h），过半仍无 B 交付就 abort 查因，不熬夜等。
- **换小档模型（flash 类）做逐格核读时，第二关不能沿用抽样密度**：从「抽 2–5 格页图」改成全量脚本比对（`check/verify_table_cells.py` 全表 + `scripts/check_lookup_ranges.py`），vision 抽核降为抽检。模型的「手」换了，抽样标准要跟着换。
- 订阅额度有限时**先跑一章探路**，量出单表 token/时间，再决定同批押不押第二、三章。
- **B 要拆段，不能一个子代理包整章**：同一子代理依次读完 20+ 张宽表，上下文只增不减，实测每调用 input 从 ~110k 抬到 ~230k，单表成本从 1.10 M 涨到 2.59 M（2.4 倍）——章节表少（≤10 张、窄表）时串着做没问题，宽表/多列表（安装尺寸、公差表）必须每 8–12 表切一段、每段新开子代理，段与段串行不占额外并发位。派工令里写清「本段只读表N-a~表N-b，交完即结束，不要接着读下一段」。改后实测：14 张公差表 = 18.2 M、**1.30 M/表**，每调用 B1 86k / B2 66k / E 46k / 主会话 49k——回到 ch07 量级，说明这两条（拆段 + 新任务）是配套的，只做一个仍会偏贵。
- **跨章续跑新开会话，不要在同一个会话里连发「继续」**：上下文只增不减，实测主代理单次 input 从 4.9 万涨到 17.5 万 token（3.5 倍），子代理是新开的所以不受影响，但主代理那一路本身会多花三倍——一章（或一批）一个新任务、dispatch 当首条消息，上下文回到 4–5 万。
- **额度护栏用两道线，不是一道**：先按「剩下的留给验收返工」算出绝对数（3 亿 → **硬停 2.85 亿 = 95%**），再设一条**只报账不停手**的通知线（2.55 亿 = 85%）。只在 85% 就停是错判：队列与单价都已实测时（表数 × 单表 token），提前停会多付一轮**不可省的固定开销**（新会话首调用 5–6 万 input + 每章一次验收往返）。实测口径：已用 0.94 亿 + 余 118 表 × 1.3 M ≈ 1.53 亿 = 2.47 亿，正落在 85% 与 95% 之间——按 85% 停手等于把够用的预算浪费掉，还得再来一轮。但 95% 必须坚停：被上游硬拒时半批状态不明，比按线停更费钱。
- **护栏是按阶段算的**：监视器按 `started_at >= 本阶段起跑时刻` 聚合，换新会话/新任务就要换时间窗，这时传的是**剩余预算**（总硬停线 − 已用），不是总预算；通知线同理。两个阈值都做成命令行参数，别在监视器里写死。
- **监控不能因为「提醒发不出去」就退出**：通知通道会失效（iLink 报 `session not ready (ret=-2)`，要用户先给 bot 发一句话续窗，能连续失败几小时）。监视器里发通知失败只许打印并继续轮询；交批状态**必须同时落盘**（`PAUSED-*.md`、验收记录、进度表），微信永远只是附加通道。实测某轮交批时微信连败 3 次，监视器按「重试 3 次后返回」直接退出，后面 40 分钟无人看管，用户回来才发现提醒没送到。同理，监视器进程退出码要能区分「真交批 / 额度停 / 卡死 / 通知挂了」，别一律 exit 0。
- **额度耗尽的停机条款要写进任务书，不能只在聊天里说**：明写「任一请求返回额度不足 / `402` / `403` / `quota` / 连续 3 次限流 → 立即停手、把已完成部分写盘、写 `STOP-额度.md`（最后完成的表号 / 已写文件 / 上游原文错误）→ 结束会话」，并禁止它换模型、降级或重试刷屏。监视器判据别靠日志关键词猜：`~/.zcode/cli/db/db.sqlite` 的 `model_usage` 有 `error_type` / `error_code` / `error_message` / `finish_reason` 列可直接查。额度口径（缓存读是否计费）跑完第一章后拿用户的额度页对一次，再报整批工期。具体阈值见上面两条（85% 报账 / 95% 硬停），依据是单表实测 token，不是拍脑袋的百分比。
- 这类临时参数（模型 / 档位 / 并发）只写进 `_批队列.md` 与当批任务书，**不改本 skill 的默认口径**；哪天恢复默认也只改那两处，并在批队列里留一行「本轮临时参数」与「默认口径」（主选 provider / 模型 / `high` / 并发数），免得下个会话把临时当常设。

## 批次授权是常设的：「停下」不等于撤销

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

> **本节讲的是机制，不是当前授权状态。** 当前状态永远以 `books/<book>/_批队列.md` 为准，且两处必须同步：用户改计划（收手 / 暂缓 / 只做某几章）时这里也要改，否则下一个会话会照本节的默认读法自动续批。当前：**每批一问**（批1、批2 做完收手，批3 起暂缓）。

用户说「批1 验收通过后自动发继续跑到批5（任一批不过就停）」是一条**常设授权**，不是一批一问。此后他再说「现在立即停下」，通常是在叫停**当轮**动作（模型跑错了、要改配置、机器要睡），**不等于撤销这条授权**——把停手读成撤权，他醒来只会问「我不是授权到批5 了吗」。

- 授权一到手就落成状态文件 `books/<book>/_批队列.md`：批次表（每批章号）、当前会话 id、每批验收状态、模型约束（主选/备选/档位）、已知坑。上下文压缩后照它恢复，别靠记忆复述。
- 每批走同一条链：交批 → 三关验收 → 过则写验收记录（`books/<书>/验收记录.md` 里按批一节；旧书曾用独立 `批N-验收.md`）+ `批N-快照.sha256` → **立刻**派下一批并重启监视器（`scripts/watch_batch_run.py` 通用版：`--signal-glob 'PAUSED-*.md' --min-batch N+1 --budget <剩余> --stall-min 20`；一次性脚本已删）；不过则停，写清哪一关挂了、差什么。
- 拿不准「停下」属于哪种，把两种解释都摆出来让他一个字定（「接着跑」/「全停」），别默默按一种执行；也不要反过来每批都去问一次。

## 报进度时别只念进度表

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

进度表是**章收口才回写**的：正在做的章仍显示「未开始」，文末「累计」（已验收章数 / 累计断言）基本不更新。用户问「跑到哪了」时取三处证据：`handoff-chNN/` 的 JSON 数（B1/B2/C/D 齐没齐）、`lib/<book>/*.py` 的 mtime 与体积、`model_usage` 按章时间窗的调用数；断言数按各章 `_tests.py` 实数累加，别抄「累计 0」。

**说「收口/收官」之前，把当初计划里列过的每一项逐条对一遍，没做的明写。** 章库跑完不等于交付完：索引对账、跨页普查、空值定性、公式落函数这些是计划里的独立项，用户会拿自己的清单问「那个索引和 diff 做了没」。报收官时给一张「项 → 状态（已完成/未做/记已知边界）」的短表，比一句「全书完成」更省一次来回。

**状态真相只有两个文件，记忆不算。** `books/<book>/沉淀进度.md`（逐章状态 + 累计）与 `books/<book>/_批队列.md`（批次、授权、会话 id、修复清单）。记忆里只留一句指向它们的指针，**不写章数**——写了必漂：实测 MEMORY.md 记着「21 章仍未开始」而进度表里 8 章早过了三关，照记忆答就是当场报错状态。用户问「做到哪了」，先读这两个文件再开口。

**用户签字（说「已验收」）要一次落五处**，少一处下个会话就报旧状态：① 进度表该章行「待验收（自检已过）」→「已验收（抽查过）」；② 文末「累计」的已验收章数 + 签字日期；③ `_批队列.md` 记一行签字与当前批次授权现状；④ `references/books.md` 里该书那一行的状态列；⑤ 当时那批验收记录（`验收记录.md` 对应节；旧书是独立的 `批N-验收.md`）。④ 最容易忘而下次会话最先读它（它是书索引）——实测它落后了两批还写着「21 章 `未开始`」。五处改完一起 `git add` 提交，两份 skill 副本用 `./sync-skills.sh` 同步。

**签字往往晚于验收记录一天以上（他甚至可能在另一个会话里签）**：验收文档里写的「待用户签」在当时是对的，**不要回改正文**——末尾追加一段「## 签字（补记）」写明哪天签、哪几章、累计变到多少，并留一句「本文件前面的内容保持验收当时原样，作为当时证据」。事后回改证据文件，等于让「三关结论」变成签字结果的回声。

**签字 / 改计划常发生在别的会话（或仓库搬家之后）**，本会话的文档不会自动跟上。用户说「校验真实情况、看和记录有没有出入」时，跑 `scripts/verify_book_state.py <book> <lib_dir>` 把「快照 hash / 实跑断言 / 进度表状态 / 契约文件 / raw 是否被写」一次对完，再拿它的输出逐条对验收记录——**快照全绿不等于文档全对**（快照只录产物文件，不录进度表与验收记录本身）。出入要么是他隔天做的事（补记即可），要么是真没跟上（当场补齐），别把两者混为一谈。

## 单价与工期：用这组数回答「怎么这么久」

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

表型手册实测（headless CLI、`high` 档）：**9–10 分钟/表**（8 表 72 分钟、17 表 168 分钟）；每章 445–895 次调用，单次 input ≈12 万 token（90% 命中缓存），平均 13 秒/请求。据此：批1（106 表）≈17 小时，全书 270 表 ≈40 小时；而图样标准那本 62 张表跑满 5 批约 20 小时——本书表量是它的 4.4 倍，节奏正常不代表卡住。

**图上的曲线是另一个价目，按「分图段」算，不按表算。** 实测（`deepseek-flash` / `high`、5 路并行）：6 个分图段（图里 a/b/d/e 一分图一段）跑到 14 分钟、243 次调用、输入 1,918 万 + 输出 35 万 = **19.5 M token**，合 **≈6.5 M/分图段**；同期表型章库是 1.1–1.3 M/表，差约 5 倍。原因在活：每段要先做标定（找网格线、拟合刻度）、再逐列扫黑、来回调参，而表值只需定位行格。
- 派这活先用「分图数 × 6 M ≈ 预算」，并把任务书按段切开、每段一段预算；按表量估会低报四倍左右。并行 5 路时约 1.2 M/分钟，离硬停线五分钟就能烧完 6 M。
- **撞线后的处置顺序**：先停（见上条 kill），再数盘上落了几段 handoff（`ls books/<book>/handoff-*/`），把「已交的段」和「半路只剩扫描脚本的段」分开报；库代码只要没动（`git status` 里只有 handoff 与 scan 脚本）就不算半合并，可以只验已交的那几段再让用户决定续不续，不必须重跑整批。
- **可以分开买的段要先报价**：哪些分图有批六那种「六线交叉、无锚点」先验（注定做不成）、哪些只差一张，派活前写清，别把注定亏本的段与好做的段绑在一个预算里。

提速只有一条不动核对标准的路：大章（50 表那种）先一次性核完「表号 → 页定位」，再按表段分 4–6 个子代理并行读表、统一合并。**别拿「纯数值表只靠 OCR 交叉核」换速度**——那是用错值风险换时间，与零猜测直接冲突。

## 验收三关（不许采信自述）

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

1. **双解释器**：`mdkit.py test all`，python3.12 与 python3.9 退出码都要 0。
2. **表值逐格**：`mdkit/check/verify_table_cells.py <lib> <表名> <页图…>`，输出覆盖行数与不一致格数。
3. **例题全链反算**：只用库函数 + 书上输入，与书上印的中间值逐项比，容差 0.5%。

三关全过才算"能调用"。完整判据、偏差归因、OCR 伪影与状态词规矩见 `references/formula-library-acceptance.md`。

**跨页判定：`续表` 必须归属到表，不能只看「这页有续表」。** 续页上的「续表」通常属于**上一页起始的那张表**。实测：表1-40（清单 [22,23]）、表14-4（清单 [201,202]）都因「本页有续表」被误判成跨页，续表实属表1-39 / 表14-3；反过来表14-3、表14-6 又因清单漏记续页被漏判。可靠判据：**看「起始页 +1（或 +2）」有没有续表或重印表题**，不看清单给的页里有没有续表。`check/span_check.py` 按此写死，与 8 条人工页图裁决全一致（表1-25 单页 / 1-39 跨页 / 1-40 单页 / 3-9 单页 / 14-3、14-5、14-6 跨页 / 14-4 单页），可用 `--check` 复跑。

**齿轮公差表的行标签是「d 档 / m 档」两段式（全书 238 条），`_区间()` 一律解析不出。** 形如 `20<d≤50 / 2<m≤3.5`，`_区间` 返回 None，于是这批表只能按整行字符串精确查，无法按「d=30、m=4」这种工程输入查。解法：`_lookup.区间取2(表, d, m, 列键)` + `_段()` 解析，**别去改 `_区间`**（锁着回归）；行列都是区间的（表10-15/10-16）用 `区间行列取`。

**`_full_ocr/pNNN.txt` 的页序号 = 印刷页 + 12**（表10-5 在印刷 133/134、OCR 落 p145/p146，已实核）。写成 `印刷页 - 12` 会让全表扫出「OCR 里找不到表号」，看着像扫描糊，其实是页码算反。另：各章 `raw/assets/handbook/<ch>/pNNN.png` 是**章内编号**（p001 = 章首页），两套编号不能混用。

**扫表号要同时试「表3-12」和「表3 12」两种形态。** OCR 常把连字符吃成空格，只用 `表\d+-\d+` 会把实有的表判成「清单漏登」，导致错误地追加一张表。反过来，清单缺号也可能是书本来就缺，回页图看一眼就能定。

**派工令里的路径要写绝对路径，不要用 `…/raw/assets/...` 缩写。** 实测有执行方把 `…` 解成相对 mdkit 的路径，得出「本仓库没有页图」的错误结论，于是改用 `books/handbook/_full_ocr/pNNN.txt` 纯 OCR 干活——笔记类散文尚可，但软件截图页必须原生读图才能判断有无数值。页图实在 `~/Documents/Obsidian/机械知识库/raw/assets/handbook/<ch>/`。

**同一路读出来的两份东西，0 差异只证明「一致」，不证明「与书一致」。** handoff 的 B.json 与章库常是同一条链（子代理读图 → 主代理原样入库），漏读会**同源同错**：实测某章 5842 格逐格比 0 差异，而表里 132M 行的 B 列（书上印 178）两边都缺，是回页图抽核才抓到的。所以第二关必须配两条独立动作：① 跑 `scripts/scan_missing_cells.py <模块名…>` 把「空值且无 merges 覆盖」的格全列出来（实测一章 156 处，多数书本来就空，但要逐处写结论）；② 抽核点里**必带一处「看着像空/看着像合并」的格**，不抽满格好认的行。抓到漏读就改库 + 在 `*_tests.py` 里加一条锁该行邻值的断言，别只改数据。

**增量/补漏型任务的验收要额外出「只增不改」的证据。** 往已验收章库里补表（补漏、拆子块、补合并区）时，逐格比对只证明新表对，不证明旧表没被动过。判据是 `git -C <repo> diff -U0 lib/<book>/<章库>.py | grep -c '^-[^-]'` **必须为 0**（纯追加），外加该章 `*_tests.py` 断言只增不减（89 → 195 这种）。执行方还会顺手改 `表清单.json` 补登漏表——那份要先备份 `.bak-before-<事件>`、按表号重排、再重建索引，三处（清单 / 索引 / 进度表）表号数才对得上。

**但有些「补数据」任务的启用动作本身就是删行。** 往库里补曲线的分材料分支时，新材料要能查到，必须先把它的键从「未数字化」常量里移走（`_图10_20_未数字化材料` 这类元组）——这时把「删行必须为 0」写死，执行方就会加一套影子常量绕过去，库里出现两套真值。判据改成白名单：任务书里点名「唯一允许删除的位置 = 常量 X / Y」，验收不再数 0，而是把 `grep '^-[^-]'` 的每一行归类——**出现白名单外的删行、或删了键却没加对应数据块，都退回**。回执里写明「本次数字化了哪几个键」，与删除行数对得上才算纯替换。

**非阻塞缺陷记清单、不打断主线。** 验收时扫出来的问题分两类：影响本批表值的当场修（改库 + 加断言）；只是「可能有问题」的（如全章 156 处空值待逐处定性、复杂版面表只能按行标签查）写进验收记录的「已知缺口」并汇总成一条待办，**全书跑完统一做一次**——插进跑批中间等于让主线为局部问题停一次、还多付一轮会话固定开销。但清单要写明「哪章、哪表、多少处、判据是什么」，下次不用重新扫一遍才知道从哪开始。

**逐格比对要按行序，不要按行标签配对。** 表里常有重复行标签（表7-2 按润滑脂种类重复「1号…4号」、表7-14 有两条 `d=30`：D=42,47,(50) 与 D=52），按标签 `dict(rows)` 配对会拿错行、报出一堆假不一致（实测 1597 格里假报 24 处，改行序后归零）。先断言 `rows_b == rows_lib` 再按 `zip` 逐格比。

**`check/verify_table_cells.py` 在这套布局下要两件事**：① 模块参数给绝对路径（它按 `SCRIPTS / f"{mod}.py"` 加载，传相对名会去 `check/` 下找）；② `check/ocrbox` 不存在时先 `ln -s ../bin/ocrbox check/ocrbox`（脚本硬编码 `SCRIPTS/'ocrbox'`）。
   全中文行标签的表（材料、润滑剂、工况）这套 OCR 对齐覆盖会是 0/36 —— 不是值写错，是它对不上 token，必须改用「handoff↔库逐格 + 人工裁图核」两条证据。

**免费 plan 的 flash 模型成本实测**：GLM-5.3-Flash（Start Plan）+ 并发 2 位，ch07 19 表 = 20.87 M token、1.10 M/表、71 分钟，cacheRead 占 94.9%；同书 deepseek-v4.1-flash 历史是 4.07–4.64 M/表 —— 差约 4 倍。估算「额度够不够」用这个口径，别用调用次数。

**B 的分段要按版面工作量，不要按表号个数对半。** 表号分一半不等于活分一半：ch05 把 8 表对半，后 4 张是弹性挡圈/圆螺母宽表（60×11、65×10），B2 每调用涨到 130k，半章 1154 万 token；ch12 更糟（一个 B 包整章 21 表，228k/调用）；ch08 的 B2 包 6 张联轴器表，77 次调用 12.4M、161k/调用。派工令里好的写法：「宽表（≥15 规格行或 ≥10 列）一段不超 3 张」**加上「一段的规格行总数不超 150 行」**——行数比表数更决定上下文膨胀，型号多的表（联轴器/弹性挡圈/圆螺母）尤其要按行切。

**拆波次要留出「整合」的余量。** 整章塞进一个时间盒时，B1/B2/E 三波常把时间吃光，留给整合 F 的是 0——ch05 就停在「材料全就绪、库未建」。两个对策：① 时间盒按「核读 60% + 整合 40%」切，别只算核读；② 真撞了也别重跑 B：单开一个「只整合」任务，读现成 JSON 机械转 py（脚本转换，不手抄），只花 3–6 M token 就能收尾，远便宜于重核。

**子代理并发要写死在派工令里。** 不写死，执行方会成批开：ch02 一次同时起 4 个，3 个立刻被 plan 的 `user concurrency limit exceeded` 拒掉（每路 1 次空调用，浪费小但会打乱节奏），随后才自己收敛成一个一个开。派工令写「同时最多 2 个子代理，第三个必须等前一个交件」即可避免。

**监控别把「并发超限」当额度耗尽。** `error_type=rate_limited` 里同时包含「额度/频率限制」和「user concurrency limit exceeded」两种含义，后者重试就好。判据按 `error_message` 区分：含 `concurrency` 的只告警不停机；真额度耗尽看 `insufficient/quota/402/403/余额`。
外部 agent 自称"已验收"一律当"待验收"，由验收方改。

## 逐格对账：handoff ↔ 库（第二关的自动化部分，几分钟顶半天抽查）

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

外部 agent 交来 5 个章库时，「抽 5 格没问题」证明不了另外 26,000 格。跑 `scripts/audit_handoff_vs_lib.py handoff-ch04 key_ch04 handoff-ch06 bearing_r_ch06 …`（在 `lib/<book>/` 下，参数成对），它把 handoff 里核过的每一格与库里落的值逐格比，按章报「表段 / 配上 / 比对格数 / 值不一致」。判据是**不一致 0**；配上比例低说明库把表拆细了（正常），配上但值为空才是问题。

三个假阳性不处理会白花一小时，算法里必须内建：

1. **一个表号 → 库里多个字典**：表4-6 拆「圆柱销/圆锥销」、表6-5 拆 49/69、表10-6 拆 T05~T12。配对键是「表号 + `rows`/`cols` 完全相同」，不是表号；否则第二份会被拿去和第一份比，报出一堆「M6 vs M8」这种假错位。
2. **重复行标签**：表9-8 有 7 行都叫 `—`。用 `rows.index(标签)` 对齐会把所有重复行钉到第一行，报出「handoff=Ⓛ lib=Ⓜ」的假差异（实际库和 handoff 一模一样）。**`rows` 列表逐项相等时一律按下标比**，只有列表不等才退回标签匹配并单独报「行标签不一致」。
3. **轻量 schema**：有的 handoff 只把 `rows`/`cols` 写成**数量**（int）+ `cols_desc`，没有行标签数组。这类按数据块尺寸（行数×列数）配对后逐格比，别当「rows 不是列表」跳过去——那正是最重的一章（表10 的 27 段全成了这种）。
4. **镜像 handoff / 键名变体：报「0 表段」不是「零差异」**。有的章（流程型/图例型）交来的 handoff 是「先入库、后从库导出」的镜像，键名还换成了 `表`+`ref` 而不是 `tables`+`表号`——对账器读不到表段，输出「handoff 表段 0 · 比对 0 格」，看上去干干净净，实际**一条证据都没验**。判据：`配上 0` 而库里有字典，就要在验收记录里写「本章无独立证据，改走页图抽核」，绝不能把 0 格当通过。镜像型章（装配图/零件图标注）本来就没有逐格表值，抽核抽的是「图上标注条目 vs 库里的 D 清单」。

**「未核」要自己核一遍**：它申报「ch10 有 14 张表未核」时，用 `表清单.json` 该章表号集合减去库内表号集合，差集必须**正好等于**申报的那几张（实测 52−38=14，恰好是 表10-27~34、10-47~52）。差集比申报多 = 有表悄悄丢了；库里有申报未核的表 = 造了值。两种情况都别签。

**页图抽核（第三关）用坐标 + 裁剪，不要读整页**：`bin/ocrbox raw/assets/<book>/chNN/pNNN.png | grep 表N-x`/`grep 关键行词` 先拿到 `x y w h 文本`，按 y 带裁出表体，再让 `vision_analyze` 直读那几十行。四个坑：**表题坐标不等于表体坐标**（表题 y 之后常是示意图，第一刀常裁到轴承剖面图而不是数据行，看型号列的 y 再裁第二刀）；**一页常上下摆两张不相干的表**（实测某页上半是表2-5 铸造碳钢、下半才是表2-6 碳素结构钢，按页码粗裁会把邻表的值当成本表的值核）；**PIL 只在 `/usr/bin/python3` 里有**，`~/.local/bin/python3.12` 会 `ModuleNotFoundError`；**一页可能摆着好几张图、每张图各有自己的「技术要求」**——实测某页同放齿轮与轴两张零件图，齿轮那块写「未注圆角 R3」、轴那块写「R1.5」，裁错区域就会把邻图的条目当成本图的值、反过来误判库写错了。抽图之前先 `ocrbox` 抓「技术要求」「未注圆角」这类**条目词**的 y 坐标确认落在哪一块，或先定位图题再裁。每章抽 2–5 格就够，但必须抽**跨类型**的（数值档位 / 符号集 / 公式型尺寸规则各一），别三格全在同一张表。

**判合并格用几何，不要凭缩小图看边线。** 合并格里的数字是**居中**的，所以它的 y 中心落在两行中心**之间**；单行格的数字落在本行中心上。做法：`ocrbox` 拿行标签列（机座号/型号/档位）每个 token 的 y 当行中心，再拿候选值列的 y 比——差半行就是合并、正好压在行中心就是单行。4 倍裁剪（PIL `resize(…, LANCZOS)` 到 1200 px 宽）只用来复核结论，缩小图上「100 到底占了 80M 还是 80M+90S」这类判断实测会读错。反过来也别把标准尺寸凭记忆当证据（表里 90S 的 B 到底是 100 还是 125，只有页图算数）。

**跨度的判读（横杠、贯通线、合并区起止）只能看原始像素，不能看缩图。** 那些「加工方法 × IT 等级」「精度等级 × 尺寸段」的表，格内不是逐格填值而是一条横杠贯通若干列；按半尺寸缩图读，横杠起止会整段偏一档，于是得出「库里 ● 位置整体左移了一档」这种**看起来极有系统性的假结论**。规矩：① 定位用缩图，判值/判跨度回原始图；② 密集表按页高切成上下两半、各自原尺寸裁，逐行报「起→止」；③ 得到「整体偏移」这种结论时，先当自己的读图比例读错了，复读一遍再定性——系统性偏差更容易来自观察方式，而不是数据本身。

## 合并 handoff 时的断言写法

> 自 `SKILL.md` 下沉（2026-10-26，正文未改）。

**合并 handoff 时期望值要手算成字面量，别在断言里重写公式。** `assert 查(材料, 硬度) == k*硬度 + b` 是把 handoff 的系数拄进断言，库里系数写错也照样绿（同源自证）；正确写法是用 handoff 的 `(k, b)` 自己算出数值、写成字面量放进断言，库里改了系数就红。

# 表型书的索引层：从 274 张表里找到对的那一张

> 口径：本文写于手册补登 4 个表号之前，正文里的「270 表」= 当时口径；实际 **274 表号**（2026-10-26 复核）。

## 为什么是索引层，不是查表优化

`取(表,行,列)` 是微秒级，慢的是**调用方不知道用哪张表、哪一行、哪一列**。实测口径（三章 71 个表字典 / 12,850 格）：
`取()` 5.2 µs、`行()` 38.8 µs、单章 import 0.01–0.04 s；全书 270 表约 500 个字典 / 5 万格 / 2 MB，全量 import 几百毫秒。
所以别再优化查表本身，缺的是「用途/已知量 → (表号, 行键, 列键)」这层映射。

## 两层，成本差一个数量级

| 层 | 内容 | 依赖 | 成本 |
|---|---|---|---|
| **A 找表** | 表号 → 表题 → 章/印刷页 → 是否已入库 → 库内字典名 | 只要 OCR 源 + 库文件 | 一次脚本，分钟级 |
| **B 定位** | 用途/已知量 → (表号, 行键, 列键) 或判据函数名 | 该表**已入库**（行键/列键存在） | 跟章走，每章一行/表 |

**A 层可以在零章沉淀时就跑完**，它回答两个问题：「查得表号查不到值」（还没入库）与「这批还剩哪些表」（工作清单）。
**B 层不许提前做**：未入库的表没有 rows/cols，用途只能猜，与零猜测冲突；而且等全书做完再补，等于拿不在手边的表凭记忆写，返工率最高。

## A 层：表题抽取

```python
import re, json, glob, os
pat = re.compile(r'^\s*表\s*(\d{1,2})\s*[-—–]\s*(\d{1,2})\s*[ 　]*(.+)$')
found = {}
for f in sorted(glob.glob(src + '/ch*-全章OCR.md')):
    ch = re.search(r'ch(\d+)', os.path.basename(f)).group(1)
    for line in open(f, encoding='utf-8', errors='ignore'):
        m = pat.match(line)
        if m and m.group(1) == str(int(ch)):
            key, title = f'表{int(ch)}-{int(m.group(2))}', m.group(3).strip()
            if key not in found and not title[:1].isdigit() and len(title) >= 4:
                found[key] = title[:48]
```

三个过滤条件都不能省：① 章号要等于文件名里的章号（正文会引用别章的表号）；② 首字符是数字的多半是表体的续行（`表6-8 max 32 35 40 …`），不是表题；③ 取先到的一条（续表/正文复述都在后面）。

命中率不要求 100%：一本 270 表的手册能一次抓到九成以上，余下是表题被拆行、表题页是整页图、或 OCR 把 `表` 和号分到两行——回页图补，或放宽正则（允许 `表 N - N` 带空格）。把没抓到的表号列出来当待办，别让它们静默消失。

**表题抓不到时，先回落到章库的 `表名`，再谈回页图。** 建库的人早把表题写进了 dict（`'表名': '平键尺寸与键槽（GB/T 1096—2003）'`），`_index.py` 里加一个 `_libmeta()`：枚举各章库含 `表号` 的 dict，取 `表名`（去掉行首 `表N-N` 前缀）与整数 `页` 做兜底，OCR 表题优先、库内表名其次。实测 20 张缺表题一次修掉 18 张，零额度、零读图。

**剩下的漏网多半是「竖排表题」，这时别用字典变量名冒充表题。** 手册把窄表的标题**竖排在表格左缘**（`rotated` 文本），`ocrbox` 按行聚字抓不到，把左侧条带裁下来 `rotate(-90)` 再读也常被截断（表题比窄表还长，跨到下一屏）。做法：列进「已知缺口（缺表题 N 张）」并写明原因，等人工回页图抄；**不要**拿 `表12_10_YZR凸缘IM3001IM3003` 这种变量名反推成表题写进索引——那是推断，不是书上印的字。

## 三方对账：表清单 ↔ 章库 ↔ 索引

A 层跑完、全书入库之后必做一次对账，工具 `check/index_diff.py`（`--md out.md` 出对账单），四条判据分开报，不要合并成一个「不一致数」：

| 判据 | 含义 | 期望 |
|---|---|---|
| A 集合差 | 清单有库无 / 库有清单无 | 双向都 0 |
| B 页不一致 | 章库 dict 的 `页` 不在清单 `pages` 里 | 0（否则必有一边错） |
| C 缺表题 | 索引 `表题` 为空 | 越少越好，逐条写原因 |
| D 跨页候选 | 清单 `pages` ≥2 页或 `continuous` 非空 | 只作待核清单，不是错误 |

B 判据能抓到的错几乎全在**清单**这一边，三类形态（都实测过）：① **`pages` 记的是「这页出现过这个表号」而不是首页**——正文交叉引用「见表9-7」会被当成页，清单记 109 而实表在印刷 120；② **OCR 三位数误读**：`151` 读成 `751`，同一页三张表全错；③ **漏位**：`244` 记成 `24`。裁决一律回页图（`ocrbox` 抓该页首行/表题），裁决完才改清单。

改 `表清单.json` 的规矩：先 `cp` 备份成 `.bak-before-<事件>`；只改 `pages` 并在该表 `note` 里留一行「日期 + 依据（页图/验收记录）+ 原值→新值」，事后能审计；补登漏号后按表号数值重排（`key=lambda k: (int(ch), int(no))`）、刷新该章 `table_count`；最后**重建 `索引.json` 并重跑 diff**，两处都归零才算收。改完别忘全书表号数会变（补登 2 张 → 272 变 274），收官总表与进度表同步。

「是否已入库 / 库内字典名」用枚举，不靠命名约定：

```python
import importlib
for name, obj in vars(importlib.import_module(mod)).items():
    if isinstance(obj, dict) and 'rows' in obj and 'cols' in obj:
        ...  # 一个表号可能对应多个字典（拆表），按 rows/cols 结构配对
```

## B 层：先收 docstring，再补判定

已入库章的 B 层一半是现成的——L2 判据函数的 docstring 本就写着用途 + 表号 + 页码：

```
平键选型 | 普通平键选型：轴径 d → b×h、t/t1、配合偏差、键长校验、键标记。
视孔盖尺寸 | 视孔盖尺寸（表11-4，p.167）。单级按 a、双级按 aΣ 查档。
```

收集器做法：枚举模块里 `__module__` 等于自身的公开可调用对象，取 docstring 首行当「用途」，正则抓 `表(\d+)-(\d+)` 与 `p\.(\d+)`，得到 `用途 → 函数名 → 表号 → 页`。抓到后**人工过一遍**再入库：① 用途描述要含**已知量**（`轴径 d`、`中心距 a`），否则查不动；② 一个函数引多表要拆多条；③ 没有 docstring 的函数直接列进「缺用途」清单，别自动填。

建库时顺手补的条目格式（写进 `books/<book>/索引.json`）：

```json
{"用途": "平键尺寸与键槽", "已知量": ["轴径 d", "键长(可选)", "配合类别"],
 "表": "表4-1", "页": 56, "库": "key_ch04", "函数": "平键选型",
 "行键": "轴d", "列键": ["b×h", "t", "t1"], "状态": "已验收"}
```

## 收尾顺序（别把索引做成独立阶段）

1. A 层全量 + 已入库章 B 层（约一小时，只读现成产物，不动已验收章库）。
2. 继续跑章沉淀，**任务书里把「本表索引条目」列为每章固定产物**——建库的人表在手上，写条目几乎零成本。
3. 全书对齐（270 表全覆盖、口径一致）放最后，那时它才真的「需要章库做完」。
4. 一维接口表达不了的二维档位（`区间取2(表, d, m, 列)`）**不依赖全书**，随时可做，别和「全书对齐」捆在一起等。
5. **对用户讲这三步必须带编号和前提**。三步都叫「索引」时，分两轮各说一半会被读成自相矛盾——用户会直接质问「你之前不是说不用等全书做完吗？怎么现在又说该等批4/批5」。正确说法是同一段里给全：①A 层薄层（现在，只读 OCR 与库文件）②每章 B 层条目（跟章走）③全书对齐（等最后几章入库）。用词上把 ③ 叫「对齐/对账」，别也叫「索引」。

## 验收探针

- **A 层覆盖率**：表清单的表号集合 − 索引表号集合 = 空；差集非空就报缺哪几个（不是「大概齐」）。
- **B 层不空转**：索引里每条的 `表` 必须能在库内找到对应 dict；找不到说明把未入库表写成了可查（等于造值）。
- **按用途真查一次**：随机抽 5 条，用「已知量」现造一个输入值走 `区间取()`/判据函数，必须出数；出不来是行键/列键写错或区间解析缺形态（后者先去跑 `scripts/check_lookup_ranges.py`）。
- **别信文件名**：`<主题>_chNN.py` 里的字典数、表号覆盖，一律 `import` 后枚举核对，不按模块命名推断。
- **三个「表数」互不相等是常态，换算等式必须成立**：已入库表号集合 / 库内字典数 / 表清单表号数 三者一般不相等（一个表号拆成多个字典 → 字典数 > 表号数；合并表或缺表 → 表号数 > 字典数）。真正必须相等的只有一条：

  `表清单表号集合 − 已入库表号集合 = 未沉淀章的表号 + 进度表里明确申报的未核表号`

  实测 270 − 99 = 171 = 157（13 个未沉淀章）+ 14（某章申报「未核」的表10-27~34、10-47~52），与进度表逐一对上。多出来的表号 = 有表悄悄丢了；少一个 = 造了值。这条等式一次覆盖全部已入库章，比逐章拿 `表清单` 对账快，也是「账本干不干净」最省力的证据。
- **对外 API 固定这五个，别每本书重新设计**：`表(表号)`、`找(关键词)`、`用途(关键词)`、`未入库(章=)`、`统计()`，外加 `python3 _index.py build` 写 `books/<book>/索引.json`。生成器要吞掉「某章 import 失败」（打 warn 继续），否则一个坏库会让整层索引一起挂。

## 查询层坍陷比测试变红更阴险

> 自 `SKILL.md` 下沉（2026-10-26 文档整理，正文未改）。

两类坍陷都满足「表在、测试全绿、值查不到」，只能靠专门探针抓。

**① 合并区回落**：表 JSON 的 `merges` 支持两种写法：3 元 `[首行,末行,列]`（纵向）与 4 元 `[首行,末行,首列,末列]`（矩形）。只实现 3 元的 `_lookup` 会把矩形合并当成“只在首列合并”，右侧合并格**静默返回 None**。验收时专门抽一个矩形合并格直接调 `_合并回落` 看回落值。

**② 区间行标签解析不了**：`_区间()` 只认 `a~b` / `>a~b`，而书上区间档常见 `自 6~8`（首档）、`a≤150`、`—~18`、`50~120（推力球轴承）`。这些行 `区间取()` 永远 KeyError——实测 `key_ch04` 表4-1 的 `自 6~8` 让 **d=6/6.5/7/7.5/8 整段查不到**（d=9 起才正常），三章 901 条行标签里有 17 条区问行属此类。

为什么测试看不见：断言用的是**已经解析出来的行键**（`取(表,">8~10",…)`），而做题时是拿数值去查（`区间取(表,35,…)`）。两回事，必须单独验。

跑 `scripts/check_lookup_ranges.py <lib_dir>`：扫全部行标签、把「看着是区间却解析不了」的列出来，再拿每行下限+0.5 实调一次 `区间取()` 当证据，顺手报 `取()` / `行()` 的 µs/次。验收每章都跑一次，不靠抽几格。修法：`_区间()` 补四类形态（去「自」前缀、去前置变量名、下界开口 `—~b`、去尾随括注，另加全角归一），**并新建独立回归文件 `_lookup_tests.py` 把行为锁死**：9 类脏写法要能解析、7 类非区间标签（`f7`/`N7`/`M8`/纯文字）必须仍返回 None、真实表按数值查得到、越界仍 KeyError。只靠各章 `*_tests.py` 全绿证明不了修复——它们断言的是**已解析出来的行键**。另注：全角数字（`１８～２０`）在 `\d` + `float()` 下是能解析的，别把「应返回 None」写成断言。

**③ 双变量档位（一维接口结构上表达不了）**：齿轮公差那类表的行标签是两个量同时限定，如 `5≤d≤20 / 0.5≤m≤2`、`20<d≤50 / 3.5<m≤6`。修好 ② 之后全书仍有约 400 条这种标签解析不了——不是漏改，是 `_区间()` 返回值装不下二维。这类表要按 (d, m) 查，只能另加双参数接口：现已实现 `区间取2(表, d, m, 列键)`（行标签两段式）与 `区间行列取(表, 行值, 列值)`（行、列各一段），解析走新加的 `_段()`——**不要去改一维的 `_区间()`**（它锁着 27 项回归）。越界与「书上没有这一档」一律 `KeyError` / `None`，不猜邻档。**在还没有这个接口的批次里，验收报告要把双参数档位单列成「已知缺口 + 需要的新接口」，不算验收失败，但别写「区间查询已覆盖全书」。**

**④ 「整块欠录」类报告，先查列组，再区分「数据不在」和「查不到」。** 一个表号可以在同一个 dict 里用**列组**承接好几块并排的小表（`名称（X块）/示意图（X块）/符号（X块）` 重复若干组），所以「某个子块整块没录」这种结论必须先在 `cols` 里找有没有以该块命名的列组、再数行数。实测执行方只看到空值清单里几格「表头/画布空位」就报了「16 个符号整块欠录」，回页图一核，16 个符号连名称早在 dict 第 18~23 列里逐格对得上，示意图列存 null 也是全书约定。
真正常见的反而是另一半：**数据在库里、但没有查询路径**。那几块的行标签是 `1~10`（书上没有符号列作行头），符号藏在数据列里，`取(表, "δ", …)` 直接 `KeyError`——对使用者等于没录。处置顺序固定：先验证数据在不在（按列组取坐标直接读 `data`，别用 `取()` 试）→ 真不在才补数据；在就补一个扫数据列的 L2（如 `焊缝尺寸符号(符号)` / `焊缝尺寸符号全部()`）+ 断言锁死每一对，别顺着误报去重建一张重复的表。

**表量大了查表会慢吗——不会，缺的是索引层。** 实测（三章 71 个表字典 / 12,850 格 / 254 KB）：`取()` 5.2 µs、`行()` 38.8 µs、单章 import 0.01–0.04 s；按此推全书 270 表约 500 个字典 / 5 万格 / 2 MB，全量 import 几百毫秒、单查微秒级。真正慢的是**找对表**：`取(表,行,列)` 要求调用方先知道表号与列名，270 张表靠猜就是做题时的真实耗时。所以缺的是**索引层**，别去优化查表本身。

**索引要分两层做，而且不是「全书做完再补一次」的收尾工程。**

- **A 层「找表」纯脚本，不依赖沉淀进度**：表号 → 表题 → 章/印刷页 → 是否已入库 → 库内字典名。表题直接从 OCR 源首列正则抓（`^\s*表\s*(\d{1,2})\s*[-—–]\s*(\d{1,2})\s*[ 　]*(.+)$`，一次跑全 21 章 270 表命中九成以上，命不中的是表题被拆行/带续行，回页图补）；「是否已入库/字典名」用 `importlib` 枚举各章库里带 `rows`/`cols` 的 dict 得到。这一步在一章都没做时就能跑完，先给「查得表号查不到值」和「这批还剩哪些表」两个视图。
- **B 层「用途/已知量 → (表号, 行键, 列键)」必须跟着章走**：建库的人表就在手上，顺手多写一行索引条目，边际成本≈0；等 21 章全做完再回头补，等于拿不在手边的表凭记忆写用途（与零猜测冲突），而且未入库表的行键/列键根本还不存在，写了也是猜。
- **已入库章的 B 层有一半是现成的**：L2 判据函数的 docstring 本来就写着「用途 + 表号 + 页码」（`平键选型` → 「轴径 d → b×h、t/t1…（表4-1，p.56）」），写个收集器枚举模块公开函数、抓 docstring 里的 `表N-N` 与 `p.NN` 就能生成骨架，不用重读表。
- **排序**：A 层 + 已入库章 B 层（一小时级）→ 继续跑批、每章固定交索引条目 → 全书对齐放最后（那才需要「章库做完后」）。一维接口装不下的二维档位（`区间取2`）不依赖全书，随时可做。
- 产物落 `books/<book>/索引.json` + `lib/<book>/_index.py`（查询入口），别塞进 SKILL.md 或进度表。**签收前跑一条换算等式**（表清单表号 − 已入库表号 = 未沉淀章表号 + 进度表申报未核表号），它一次覆盖全部已入库章，能同时抓出「悄悄丢表」和「造值」。**对用户讲这三层要带编号与前提**（①A 层薄层 ②每章条目 ③全书对齐），否则「先做索引」与「等全书做完」会被读成前后矛盾。细节、五个查询 API 与验收探针见 `references/table-index-layer.md`。

**索引层收尾还要跑一次三方对账**（`check/index_diff.py`：表清单 ↔ 章库 ↔ `索引.json`，四条判据 A 集合差 / B 页不一致 / C 缺表题 / D 跨页候选），改清单前先备份、改后重建索引再复跑，直到 A、B 归零。**表题抓不到时先回落到章库 dict 的 `表名`**（`_index.py` 的 `_libmeta()`），实测 20 张缺表题一次修掉 18 张；剩的多是竖排表题，只记缺口，别用字典变量名冒充。判据口径与三类 `pages` 错法见 `references/table-index-layer.md`。

**「清单里没有」不等于「书里没有」**：`表清单.json` 由脚本扫表题得来，会漏（实测 ch07 漏了 表7-5，p.91 压配式压注油杯，页图上确实存在）。索引与清单对不齐时，**先回 OCR 表题正则 + 页图核一次**再决定改哪边——只信清单会得出「索引多抓了」，只信索引会让一张真题永远进不了待做队列。补登清单要先备份（`.bak-before-add-<表号>`）、按表号重排，然后重建 `索引.json`，三处（清单 / 索引 / 进度表）表号数才对得上。
